# KROWDS Monorepo

The KROWDS monorepo contains five Next.js frontend applications and one Go backend located at the repository root under `services/`. The frontend applications are managed with **pnpm workspace** and **Turborepo**, while the services are managed as a single Go module within `go.work`.

## Components

| Component | Package/Path | Port | Focus |
| --- | --- | ---: | --- |
| Web | `@krowds/web` | 3000 | Primary public frontend |
| Auth | `@krowds/auth` | 3001 | Login, registration, and session management |
| Krew | `@krowds/krew` | 3002 | Crew workspaces and collaboration |
| Org | `@krowds/org` | 3003 | Organization management |
| PWA | `@krowds/pwa` | 3004 | Progressive web application and offline app shell |
| Services | `services/` | 8080 | Go + Gin backend implemented as a modular monolith |

## Stack

- Next.js 16 with App Router
- React 19 and TypeScript
- Tailwind CSS 4
- shadcn/ui preset `b2fA` (Nova, neutral, Geist, Lucide)
- Base UI primitives
- ESLint 9
- Go 1.27.1 and Gin
- Clean architecture within each module
- pnpm and Go workspaces
- Turborepo with shared internal packages
- Google Cloud Platform: Cloud Run, Cloud SQL for PostgreSQL, Memorystore, Cloud Tasks, Cloud Scheduler, Cloud Storage, Secret Manager, Cloud Logging, Error Reporting, Monitoring, and BigQuery
- Resend for transactional email
- Xendit for QRIS, Virtual Account, e-wallet payments, and refunds
- Biteship for domestic shipping labels, tracking, and delivery webhooks

Dependency policy: use the latest stable release compatible with the installed framework. ESLint remains on the latest 9.x line and TypeScript on the latest 5.x line because `eslint-config-next@16.3.6` and `typescript-eslint@8.70.1` do not yet support the next major versions.

## Internal packages

The frontend applications use source-first internal packages linked with `workspace:*`:

| Package | Purpose |
| --- | --- |
| `@krowds/ui` | Shared shadcn/ui Components, Blocks, Charts, Typeset, design tokens, and approved compositions |
| `@krowds/tsconfig` | Base, library, and Next.js TypeScript configurations |
| `@krowds/eslint-config` | Shared base and Next.js ESLint flat configurations |
| `@krowds/types` | Shared API response, pagination, and entity ID types |
| `@krowds/utils` | Shared class-name, query-string, and string helpers |
| `@krowds/api` | Typed API client with authentication, query, and error handling |
| `@krowds/hooks` | Shared React hooks |
| `@krowds/validation` | Shared runtime validation primitives |

Next.js automatically transpiles source packages because they are part of the pnpm workspace. Runtime packages define `build`, `lint`, and `typecheck` tasks. Turborepo builds the dependency graph and runs upstream packages first.

## Validation

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm test:architecture
pnpm build
pnpm clean
```

The frontend is validated through Turborepo lint, typecheck, and build tasks. The services are validated through Go tests and Clean Architecture checks through `test:architecture`; the frontend/backend boundary is enforced as a repository design constraint during code review.

### Build artifacts

`pnpm build` produces a single backend binary at `bin/services`. The `bin/` directory is the common location for local build artifacts and is ignored by Git. It does not store source code, is regenerated by builds, and is removed by `pnpm clean`. In CI/CD, published artifacts must still come from a centralized build output directory such as `bin/`, `build/`, or `dist/`; binaries must not be committed to the repository.

## Frontend/backend boundary

Next.js handles only rendering, navigation, UI state, and browser flows. Backend HTTP APIs, authentication, authorization, persistence, queues, and business workflows are all implemented in Go + Gin under `services/`.

The boundary is a repository-wide design constraint:

- Next.js route handlers and Server Actions are prohibited under `apps/*`.
- Backend logic through `proxy.ts`/`middleware.ts` is prohibited.
- Databases, queues, and backend-only SDKs are prohibited in frontend workspaces.
- Go files may exist only under `services/`.
- The backend must remain a single composition root and binary under `services/cmd/server`.

Run the Go architecture gate after changing the backend:

```bash
pnpm test:architecture
```

## Services architecture

`services/` is a single deployable Go service structured as a modular monolith. Each business capability remains isolated as a module that follows Clean Architecture:

```text
services/
├── cmd/server/                         # entry point and composition root
└── internal/
    ├── config/                         # runtime configuration
    ├── modules/
    │   └── system/
    │       ├── application/            # use cases and ports
    │       ├── delivery/http/          # Gin handlers and DTOs
    │       ├── domain/                 # entities and business rules
    │       ├── infrastructure/         # dependency adapters
    │       └── module.go               # module wiring
    ├── platform/                       # cross-module technical primitives
    └── transport/http/                 # composition router and Module interface
```

Dependencies point toward `domain`: delivery and infrastructure depend on application/domain, not vice versa. Modules are registered in `services/internal/transport/http/router.go`, and each module is composed from `services/cmd/server/main.go`.

`architecture_test.go` also enforces the following rules:

- Every module must contain `domain`, `application`, `delivery/http`, `infrastructure`, and `module.go`.
- Only `cmd/server` may contain a production `package main` and `func main()`.
- Every discovered module must be composed into the router.
- Technical packages must not import business module implementations.
- Modules must not import other module implementations.

For cross-module collaboration, use only pure contracts in `internal/contracts` or pure events in `internal/events`. These packages must not import Gin, transport, delivery, infrastructure, or concrete modules.

## shadcn/ui

All five frontend applications follow the approved shadcn/ui style preset `--preset b2fA`. Use the official shadcn/ui **Components**, **Blocks**, **Charts**, and **Typeset** as the visual building blocks; do not create custom visual components. The `Button`, `Badge`, and `Card` primitives are in the shared `packages/ui` package, consistent with official shadcn/ui monorepo support.

When applying or synchronizing the approved preset, use:

```bash
pnpm dlx shadcn@4.21.0 apply --preset b2fA --cwd apps/web
```

After the preset is aligned, add components through the official CLI. Primitives are directed to `@krowds/ui`, while app-specific blocks remain in the application:

```bash
pnpm dlx shadcn@4.21.0 add input label --cwd apps/web
```

## PWA

The service worker is intentionally registered only in production builds so that its cache does not interfere with development.

```bash
pnpm --filter @krowds/pwa build
pnpm --filter @krowds/pwa start
```

Open `http://localhost:3004`, then use the install application menu in a PWA-capable browser.
